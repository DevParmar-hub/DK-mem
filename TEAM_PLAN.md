# DK-Mem paper: team plan (4 people, deadline: tomorrow)

**Scope (fixed by the deadline):** a *preliminary* paper. Hindi results from the stored, verified runs + the DK-Mem method + the benchmark +
the evaluation-integrity methodology + an **in-team** native review of the Marathi/Gujarati extension. **No new inference, no new test set,
no new seeds.** (Greedy decoding makes reruns identical, so extra seeds would add nothing; uncertainty is reported over pairs.)

Everything you need is in this repository. Every number in the paper is generated by a script from the verified report, so nobody types a
result by hand, and the paper is "done" when `python tools/check_paper.py` exits 0.

## 2. Native review (P2, P3, P4): how

Open your CSV in Excel/Google Sheets (UTF-8). Fill **only** the empty columns:

* `verdict`: `correct` (the same/different label is right under the stated conventions), `wrong`, or `ambiguous` (two readings defensible).
* `natural`: would a native speaker type this? `yes` / `awkward` / `no`.
* `class_ok`: is the class (kinship / honorific_register / name_variant / contextual_qualifier) right? `yes` / `no`.
* `comment`: required for every `wrong`, `ambiguous`, `awkward` or `no`. Write the reason and, if you know it, the correct form.

Rows with `repaired = yes` (Marathi/Gujarati) were changed by the assistant without native review. Review those first. Bank and lexicon
sheets take `ok` / `wrong` / `unsure` + comment. **Do not edit text, labels or ids**, only verdicts. A wrong item is reported, not silently fixed.

Labelling conventions you judge against (from `data/team_b_delivery/README.md`):
1. same name, no distinguishing qualifier = same person;
2. register shift with the same vocative = same person; different addressees = different people;
3. gold-same kinship pairs force identity with a shared name/apposition;
4. a contextual qualifier ("office wali Priya") overrides name identity.
If you think a convention itself is wrong for your language, say so in `limitations.tex` (your paragraph). That is a finding, not a failure.

Honesty rule for the paper: you are co-authors and you saw the labels, so this is **in-team, non-independent** review. Say so.

## 3. Git workflow (GitHub, private repository)

**Keep the repository PRIVATE.** Review sheets contain development labels. Never commit `teamB_answer_key.jsonl`, any `*test_gold*`, or
`data/tier2_v2_1/heldout_sealed/` (the `.gitignore` already excludes them; the test suite checks it).

### P1, once, before anyone starts
```bash
git checkout -b team/main-import
git add -A            # first check `git status`: eval/, validation/, paper/, tools/, tests/ and data/tier2_v2_1/ are currently untracked
git commit -m "Import DK-Mem working tree, paper scaffold and team tooling"
git push -u origin team/main-import     # open a PR into main, merge it, then everyone clones/pulls main
```
Large run artifacts (`eval/tier2_entity_runs/`, `results/`, `data/team_b_delivery/`) are gitignored. They stay with P1. The paper does not need them
to build, because `paper/generated/` is committed.

### Everyone else
```bash
git clone <repo-url> && cd <repo>
git checkout -b p2-benchmark          # p3-method, p4-intro, ... one branch per person
# ... edit ONLY your files ...
python tools/check_integrity.py       # must print OK
python tools/check_paper.py --draft   # shows remaining TODOs; fine to have some until the end
git add <your files only>
git commit -m "P2: benchmark section + Hindi review"
git push -u origin p2-benchmark       # open a pull request into main
```
Small, frequent PRs are better than one big one. P1 merges. If `git pull` ever shows a conflict, someone edited a file they don't own:
stop and tell P1.

### P1, merging
For each PR: `python tools/check_integrity.py` passes, `python -m pytest tests eval/tests -q` passes, the PR touches only its owner's
files, then **merge (no squash, so nothing is lost)**. After the review CSVs are merged:
```bash
python paper/tools/summarize_reviews.py                                   # review counts + paper/review/exclusions.txt
python paper/tools/make_numbers.py --exclude paper/review/exclusions.txt  # adds the sensitivity numbers; primary numbers unchanged
```
then commit `paper/generated/` and `paper/review/exclusions.txt`.

## 6. Definition of done

1. `python tools/check_integrity.py` → OK (nothing frozen changed; numbers current).
2. `python tools/check_paper.py` → OK (no TODO, no unverified reference, no undefined or hand-typed number).
3. `python -m pytest tests eval/tests -q` → no failures.
4. Every co-author has read the full PDF.

## 7. Claims: allowed and not allowed

**Allowed:** the failure mode in our constructed benchmark; Tier 2 on the Hindi pairs: the gate cut Config C's false merges from 9/36 to
1/36 at the cost of 0/27 → 5/27 missed merges; D at τ=0.90 never merged a gold-same pair. Tier 1 (isolated pairs, 3B, labels
LLM-annotated, provisional): configs A–D with and without the gate, e.g. D at τ=0.90 false merges 24/36 → 0/36 with missed merges
unchanged. All single seed, development data. The verification methodology and the prompt-identity failure case; the benchmark release with
in-team native review.

**Not allowed:** any Marathi/Gujarati *result* (none was run); "native-validated" or "independent" review; a held-out/blind test; any claim
that a τ value or the judge is a good or selected choice; natural-frequency claims; pooling Tier-1 (3B) with Tier-2 (7B) numbers; Tier-2
claims about Configs A/B (not run on Tier 2).

## 8. If something goes wrong

* `check_integrity.py` says a frozen/pinned/vendored file changed: **do not commit**; restore that file from `main` and tell P1.
* A number in the PDF looks wrong: fix it in `paper/tools/make_numbers.py` (P1), never in the `.tex`.
* A reviewer finds a wrong Hindi label: it goes to `exclusions.txt` and the sensitivity table; the primary table is not edited.
